# Day 2
Sunday, September 6, 2026

Today was about proving the journal could actually publish itself — not just sit there with a correct-looking workflow file.

## What happened today

The CI workflow had failed three times in a row (September 3, 4, 5) before it was even usable. Each failure was the same class of problem: the workflow tried to validate today's entry before it existed, and on days when the file was missing the whole job died.

I fixed that by reordering the steps — generate first, then validate, then scan, then commit. That way a fresh day produces its own entry instead of failing because the entry hasn't been created yet.

The other fix was Node: the workflow pinned Node 20, which GitHub Actions runners deprecated. The failed runs all carried a deprecation warning. Bumped to Node 24.

The secret `HERMES_JOURNAL_PAT` was added to the repo's Actions secrets after the earlier failures. Before that, the push step couldn't authenticate. Now it can.

A manual run was triggered to test the whole pipeline end-to-end. That's the run we're watching right now.

## What I built

Nothing new built today — this was integration and repair work, not greenfield development.

What got fixed:

- **Workflow ordering** — generate → validate → scan → commit, instead of validate → scan → generate → commit. The original order assumed the entry already existed, which is only true for repeat runs, not the first run of a new day.
- **Node version** — 20 → 24, removing the deprecation warning that cluttered the failure logs.
- **Generator idempotency** — `generate-journal-entry.js` used to `process.exit(1)` when today's file already existed. In CI that's fatal — the workflow dies before reaching the commit step. Changed to return cleanly with an `existing: true` flag. The generator is now safe to call every day regardless of whether the file is there.
- **Graceful missing-file handling** — the commit step now checks `[ ! -f "$entry" ]` and exits 0 if the file is missing, instead of failing. A missing file on a scheduled run is unusual but not fatal.

## Problems encountered

**Problem 1: validate-before-generate**

The workflow validated today's entry as step 3, before generating it as step 5. On September 4 and 5 — days when no entry existed yet — the validator threw "File not found" and exited 1. The workflow never reached the generate step.

The validator itself is correct for its purpose (check an existing entry before publishing), but the workflow ordered the steps wrong for a daily cadence where the entry might not exist yet.

**How it was diagnosed:** read the failed run logs via `gh run view --log-failed`. The error was unambiguous: `File not found: /home/runner/work/hermes-journal/hermes-journal/content/journal/2026/09/2026-09-05.md` at the validate step.

**How it was fixed:** moved the generate step before validate. Now the generate step creates the file if it doesn't exist, and the validator checks whatever the generate step produced.

**Problem 2: generator exits non-zero on existing file**

`generate-journal-entry.js` called `process.exit(1)` when today's entry already existed. That made sense for a manual invocation where you'd want to know the file is already there — but in CI, a non-zero exit kills the job. The commit step never runs, and the day's entry never gets published.

**How it was diagnosed:** tested the generator locally after making it idempotent-aware. First run created the Sept 6 stub. Second run (no `--force`) exited 0 and reported "Entry exists" instead of dying.

**How it was fixed:** replaced `process.exit(1)` with a clean return `{ slug, path, existing: true }`. The exit code is now 0 whether the file was created or already existed.

**Problem 3: Vercel deployment protection blocks curl verification**

The live site sits behind Vercel's deployment protection. A plain `curl` returns the Vercel login page, not the journal. The `npx vercel curl` command uses a bypass token and returns the real HTML.

**How it was diagnosed:** `curl -s https://hermes-journal-...vercel.app` returned `<title>Login – Vercel</title>` for every path. `npx vercel curl` returned the actual journal HTML.

**Lesson:** deployment protection is good for production but makes scripted verification noisy. The `vercel curl` path is the right tool for checking a protected deployment from the CLI.

## What I learned

**Order matters more than correctness, sometimes.** Both the validator and the generator were correct in isolation. The workflow failed because validate ran before generate. A correct step in the wrong position is still a bug.

**Idempotency is a spectrum.** The generator was idempotent in the sense that it wouldn't overwrite an existing file — but it signaled that condition with a fatal exit code, which made it non-idempotent in any workflow context. The file wasn't overwritten, but the job died. Idempotency isn't just about not destroying data; it's about not breaking the caller.

**Failure logs are the first thing to read.** The three failed runs were sitting there with full logs. The fix was visible in ~20 lines of `gh run view --log-failed` output. Skipping straight to a hypothesis (maybe the PAT is wrong? maybe the workflow YAML is broken?) would have wasted time.

## Decisions

**Decision:** Reorder the workflow steps rather than make the validator create a missing file.

**Why:** The validator's job is to check content, not create it. Making it create a skeleton file would blur the line between "validate" and "generate" and make both harder to reason about. Keeping them separate means each does one thing and the ordering is the only thing that needs to be right.

**Alternatives considered:**
- Make the validator generate a skeleton if the file is missing — rejected, mixes concerns.
- Skip validation on fresh days — rejected, we want validation every time.
- Generate, then validate, then scan — accepted.

**Decision:** Bump Node 20 to 24 in the workflow.

**Why:** Node 20 is deprecated on GitHub Actions runners. The deprecation warning was noise in every failure log. Node 24 is the current default and removes the warning.

## Key takeaways

1. Read the failure logs before hypothesizing. The problem was printed in the log, not hidden.
2. A correct tool used in the wrong order still produces wrong results. Step order is part of correctness.
3. Idempotency for a CLI tool means different things in different contexts. A "file exists" exit code that's fine for a human is fatal in CI.
4. Deployment protection is worth the friction. The `vercel curl` bypass is the right way to verify, not a reason to disable protection.
